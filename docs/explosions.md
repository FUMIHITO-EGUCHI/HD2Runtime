# Explosions

Every explosion in Helldivers 2 is one row of the game's ExplosionSettings table (422 rows on build F5FEE03DCFDB):
radii, the DamageInfo row its +4 member links (damage, armour penetration, demolition, stagger, push), a particle
effect, a sound, a shrapnel projectile and count, an arc. HD2Runtime names the rows from what requests them and exposes
the named ones as a catalogue you can read, edit, use as a weapon's payload and request at a position.

Nothing on this page is live-tested yet. Every edit, every payload donor and every spawn outside the reviewed set
needs an acknowledgement (below); the write paths are proven offline on the retained snapshot
(`scripts/validate_explosion_catalogue_snapshot.py`, `validation/explosion-catalogue-snapshot.json`).

- Research: `scripts/research_explosion_identities.py` -> `research/explosion-identities-F5FEE03DCFDB.json`,
  `research/docs/explosion-identities-F5FEE03DCFDB.md`.
- Catalogue: `domains/explosion_catalogue.lua` (runtime) and `sdk/ExplosionCatalogue.json` (contract
  `hd2runtime.explosion_catalogue.v1`, for ModBuilder; no raw ids), generated by `scripts/generate_explosion_catalogue.py`.

## How explosions are named

A name comes only from a typed reference in the game's own data or a literal in its request code, never from a value
or a resemblance:

| Evidence | What holds the type | Example |
| --- | --- | --- |
| projectile | a projectile row's impact (+144) or expiry (+156) explosion; the projectile is named by what fires it (research/projectile-identities) | `weapon/r36_eruptor/impact` |
| component | ExplosiveComponent +36 (the detonation), WeaponCharge +200 (overcharge), Backblast, Minefield, ProjectileCluster, Displacement, GibEntity, crash explosions of RagdollSync and VehicleCrash | `throwable/g6_frag/detonation` |
| beam, delta | a beam row's +96; a customization delta patching one of the members above | |
| code | a literal type passed to the game's explosion request (or a wrapper proven to pass its type on), in code a BehaviorId's or an AbilityId's dispatcher entry runs; the ids name their entities | `stratagem/nux223_hellbomb/behavior` |
| chain | the impact or expiry of a projectile that only a named explosion releases as shrapnel | `support_weapon/rl77_airburst_rocket_launcher/function_expiry/shrapnel_expiry` |

The id is `<family>/<owner>/<role>`. The family is the owner's: `weapon` (primary and secondary weapons),
`support_weapon`, `throwable`, `stratagem`, `backpack`, `vehicle`, `enemy`, or `entity` (an entity named only by its
resource path). The owner is the first owner by catalogue priority (player weapon, support weapon, throwable,
stratagem, backpack, vehicle, enemy, other entity); every owner is listed. Roles say how the owner requests it:
`impact` / `expiry` (with the projectile's role first when it is not what the owner fires: `shell_impact`,
`payload_impact`, `charge_2_impact`, `function_expiry`, `magazine_impact`), `detonation`, `overcharge`, `backblast`,
`mine`, `cluster`, `gib`, `vehicle_crash`, `ragdoll_crash`, `behavior`, `ability`; `inventory_` and `fired_` prefix an
entity named through the inventory item or the fired entity that holds it. Two rows with the same id are numbered
(`_2`, `_3`) in type order.

**Chains with several sources (0.31.2).** A chain explosion takes its id from the first named explosion whose shrapnel
requests it, but every such explosion is one of its owners. The RL-77 Airburst Rocket Launcher's bomblets explode as
one row. The 25 bomblets of its rocket's burst (`support_weapon/rl77_airburst_rocket_launcher/impact`) and those of its
cluster round (`.../function_expiry`) both use it, while its id, `.../function_expiry/shrapnel_expiry`, names the
cluster round only. It therefore also has an owner-neutral **alias**,
`support_weapon/rl77_airburst_rocket_launcher/bomblet`:
- `hd2.explosion(alias)`, `hd2.explosions.describe(alias)` and every place that takes an explosion name accept it;
- the handle carries the semantic id, which keeps working;
- `hd2.explosions.list({search='bomblet'})` finds it;
- the catalogue lists aliases (`aliases`, and per explosion).

The catalogue generator re-checks the alias against the research records: both bursts' shrapnel projectiles impact as
this row. The bomblet row's damage is shared with other references, so a damage edit needs `allow_shared`.

The second chain shows in the explosion's owners once `research/explosion-identities-F5FEE03DCFDB.json` is
regenerated with `scripts/research_explosion_identities.py` (0.31.2 records every named source). Names, sharing and
packages stay the same.

| --- | ---: |

| support_weapon | 32 |
| throwable | 23 |
| stratagem | 42 |

241 of the 422 types are named; 108 of them are **shared** (more than one owner requests the row). The other 181 stay
out of the catalogue, with the reason recorded in the research: 66 have no typed reference in the data and no literal
in the request code (unused rows, or types computed at run time), 40 are the impact or expiry of projectiles nothing

abilities no entity is proven to own, 19 by code no behavior or ability dispatcher is proven to run.

All 422 types are proven against the game's settings table: in every retained mission snapshot, the table the game's
explosion drain indexes by type points at a record equal to the pinned row byte for byte (outside its relocated
array).

## Packages

The effect an explosion draws is its row's particle resource. Before it can be used as a payload or requested, the
package that ships that effect must be resident. The research finds it from the installed game data:

| How | Named explosions |
| --- | ---: |
| the owner's own loadout package lists the effect | 56 |
| the owning stratagem's call-in package lists it | 35 |
| no owner package lists it; the smallest loadout package that does | 33 |
| the mission effects package (`packages/content/effects_mission`) lists it | 14 |
| a reviewed named explosion's package (Hellbombs, Cyborg Production Unit) | 3 |

141 named explosions have a package; the other 100 (most enemy explosions: their effects ship in faction content,
which the Runtime never loads) are editable but are neither payload donors nor spawnable. The mission effects package
is resident in every mission (all in-mission snapshots, none aboard the ship); the Runtime never loads it (about
300 MB): a payload that uses it needs no load, and a spawn checks that it is resident. Every other package is loaded
through the game's own package system before the write or the request (docs/asset-loading.md); its key is
`explosion/<name>`.

## Reading the catalogue

```lua
for _, e in ipairs(hd2.explosions.list({family = 'stratagem', payload = true})) do
    mod:log(e.name .. ' ' .. e.label .. (e.shared and ' (shared)' or ''))
end
local d = hd2.explosions.describe('stratagem/orbital_gas_strike/shell_impact')
-- d.owners, d.package {known, name, via, mission, loaded_by_runtime}, d.fields, d.stats, d.shared, d.damage_shared
```

- `hd2.explosions.list(filter)`: every catalogued explosion as `{name, label, family, evidence, shared, owners (a
  count), package_known, mission_package, payload, spawn, reviewed_spawn, legacy_name, stats}`. Filters: `family`,
  `owner` (a case-insensitive substring of an owner's name), `search` (of the name or label), and the booleans
  `shared`, `payload`, `spawn`, `package_known`, `reviewed_spawn`.
- `hd2.explosions.describe(name)`: the list entry plus `owners` ({category, name, role, reference}), `package` and the
  editable `fields`. A name is the semantic id or the label (case-insensitive).
- `hd2.explosion(name)`: the typed handle (`{resource = 'explosion', explosion = <id>}`, with `:describe()` and
  `:fields()`): an edit target, a payload value and a spawn argument.
- `hd2.explosions.reviewed()`: the reviewed spawn set (0.29's `list()` shape, without the raw type), each with its
  `catalogue` name.

No raw type, row, resource or package id is ever returned.

## Editing an explosion

```lua
local shell = hd2.explosion('stratagem/orbital_120mm_he_barrage/shell_impact')
hd2.ensure({transaction = {id = 'barrage-wider', target = shell, allow_unverified_effect = true, changes = {
    {field = hd2.fields.explosion.inner_radius, expect = 3.3, value = 5},
    {field = hd2.fields.explosion.outer_radius, expect = 10, value = 14}}}})
```

| Field | Row | Range |
| --- | --- | --- |
| `explosion.inner_radius`, `outer_radius`, `shockwave_radius` (m) | explosion | 0..150 |
| `explosion.shrapnel_count` | explosion (only where the row releases a shrapnel projectile) | 0..64 |
| `explosion.damage.standard_damage`, `durable_damage` | damage | 0..20000 |
| `explosion.damage.ap_direct`, `ap_slight`, `ap_large`, `ap_extreme` | damage | 0..10 |
| `explosion.damage.demolition`, `stagger`, `push_force` | damage | 0..200 / 500 / 5000 (widened to the largest vanilla value) |

- Every field needs `allow_unverified_effect`: no edit through this target is live-tested.
- `allow_shared` when the row is shared (`describe().shared`: every owner changes), or for a damage field when the
  DamageInfo row is used by other references (`describe().damage_shared`).
- `expect` is the catalogued value (`describe().fields[i].currentDefault`); patch, transaction, plan and ensure all
  work, and one transaction may change the explosion row and its damage row together.
- Every write re-proves, in the live settings allocations, that the explosion row for its type is the reviewed row
  (type, group, row, settings type) and, for a damage field, that the row's +4 link still names the reviewed DamageInfo
  row and that row's identity. A changed row refuses (`EXPLOSION_IDENTITY_CHANGED`, `EXPLOSION_ROW_ABSENT`, or
  `CONFLICT` for a changed link).
- Not offered: re-pointing the damage link (+4) or the shrapnel projectile (+84), the particle and sound, the status
  and fire templates, the arc. A row without a damage link (smoke) has read-only damage fields.
- The same rows are also reachable through their owners' own targets (a weapon's `terminal_action(phase):explosion()`,
  throwables, stratagem attacks, enemy attacks): those keep their own rules. Since 0.31.0 the CQC-20 Breaching
  Hammer's charge blast (`support_weapon/cqc20_breaching_hammer/ability`) is also its support weapon's
  `attack('ability'):explosion()` ([support weapons](support-weapon-api.md#cqc-20-breaching-hammer-blast-0310-offline-only)).

## Explosions as payloads

A weapon projectile's impact or expiry explosion can be any catalogued explosion whose package is known
(`payload = true`):

```lua
local impact = hd2.weapon('R-36 Eruptor'):attack('primary'):projectile():terminal_action('impact')
hd2.ensure({patch = {id = 'eruptor-loyalist-blast', target = impact, field = hd2.fields.terminal.explosion,
    expect = impact:explosion(), value = hd2.explosion('weapon/plas15_loyalist/impact'),
    allow_unverified_reference = true, allow_unverified_effect = true}})
```

- `terminal.explosion` (primary, secondary and, since 0.31.2, support weapons: below) and an attack output's
  `projectile.impact_explosion` / `projectile.expiry_explosion` slots (docs/attack-outputs.md) take
  `hd2.explosion(name)` as the value; the custom projectile rows' `impact_explosion` component takes it too
  (docs/custom-projectile-rows.md; infrastructure, no public definition API yet). Mounted weapons have no
  `terminal.explosion` field: their rows are reached through their attack output's slots.
- A catalogued donor is not live-tested: `allow_unverified_reference` and `allow_unverified_effect`. The existing
  donors (another weapon's explosion handle, an output's slot handle) keep their rules unchanged.
- Its package is loaded before the write (the operation waits, `WAITING_FOR_ASSETS`); a mission-effects donor needs no
  load. An explosion without a known package is refused (`ASSET_UNAVAILABLE`). The Cyborg Production Unit's (two
  objective packages) was refused too before 0.31.2; it now loads both (below, "EXCESSIVELY LARGE NUKE").
- Before the write the donor's live row is re-proven, and a donor whose shrapnel chain would release the written
  projectile again is refused (`RECURSIVE_COMPOSITION`).
- The explosion row is shared by reference only: nothing is written to the donor.

## Payloads on support weapons (0.31.2, offline only)

Support weapons have the impact and expiry payload of the primaries: `terminal.<role>.<phase>.explosion`, the
ExplosionType members (+144 impact, +156 expiry) of the projectile row an attack fires. Before 0.31.2 a support weapon
could only edit its current explosion's values (`attack('primary_impact'):explosion()`), and a payload could only be
changed through the attack output's slot (`hd2.attack_output(id)`, which some outputs, such as the AC-8 flak, do not
have).

```lua
local apw = hd2.support_weapon('APW-1 Anti-Materiel Rifle'):attack('primary'):projectile():terminal_action('impact')
hd2.ensure({patch = {id = 'apw-frag', target = apw, field = hd2.fields.terminal.explosion,
    expect = apw:current(), value = hd2.explosion('throwable/g6_frag/detonation'),
    allow_shared = true, allow_unverified_effect = true, allow_unverified_reference = true}})

-- Per fire mode: the AC-8's flak (its ProgrammableAmmo row) has its own payload, apart from its HE round.
local flak = hd2.support_weapon('AC-8 Autocannon'):attack('programmable'):projectile():terminal_action('impact')
```

- **Target.** `hd2.support_weapon(name):attack(role):projectile():terminal_action(phase)`, `phase` `impact` or
  `expiry`. `role` is every attack that fires a projectile row: `primary` (the normal round), `programmable` (the
  ProgrammableAmmo feed: AC-8 flak, GR-8, RL-77 cluster round), the charge levels (`primary` and `full_charge` on the
  PLAS-45 Epoch) and the rounds feed (`feed_primary` on the SG-88). The field is `hd2.fields.terminal.explosion` (the
  qualified id `terminal.<role>.<phase>.explosion` is the same field).
- **Values.** `terminal:explosion()` (the row's own explosion: the reviewed baseline, where it has one),
  `terminal:no_explosion()` (none), `hd2.explosion(name)` (any explosion with `payload = true`) or another weapon's
  terminal explosion handle, which is taken as the catalogued explosion it names. `terminal:current()` is the expect:
  `explosion()` or `no_explosion()`, whichever the row holds natively.
- **Acknowledgements.** Every write needs `allow_unverified_effect` (no support payload is live-tested) and
  `allow_shared`: a support projectile row is always treated as shared, and `terminal:describe()` lists who else fires
  or releases it (`consumers`, `released_by`). A catalogued donor also needs `allow_unverified_reference`.
- **Write.** The row is the one the role's projectile fields already write, re-resolved through the weapon on every
  write (ProjectileWeapon +0, WeaponRounds +64, the WeaponCharge level selectors or ProjectileWeapon +576), so a
  swapped feed or projectile refuses the write instead of editing another row. A catalogued donor's package is loaded
  first, its live row is re-proven, and a chain that would release the written row again is refused
  (`RECURSIVE_COMPOSITION`), as for the primaries. The spawn copies the row's members into each shot: the write
  applies to shots fired after it.
- **Caveats carried in the field** (`payload.notes`): the MG-43 and MGX-42 fire a magazine pattern whose tracer rounds
  are another row, which keeps its own explosions; a row with no lifetime (0) only expires through a fuse, so an expiry
  payload on it may never go off (the AC-8 flak, the RL-77 rockets, the Quasar and the Railgun have a lifetime); each
  Epoch field names its charge level.
- **Missiles.** The FAF-14 Spear, MLS-4X Commando and StA-X3 W.A.S.P. spawn a missile that carries the weapon's row as
  its hit row: its impact explosion is the row's +144 (research/wasp-rocket), so the impact payload is offered. The
  missile ends by its own lifetime, and whether the carried row's expiry explosion ever fires is not traced: no expiry
  payload is offered (`blockedFields`, and the target names the reason). The W.A.S.P.'s ProgrammableAmmo missile has
  no reviewed attack and no payload field. Changing the W.A.S.P.'s row also changes the seven submunitions its cluster
  missile releases (`released_by`), and that cluster's explosion is refused on it.
- **Proof.** Every one of the 51 fields resolves on the retained snapshot to its reviewed row and value (guarded
  no-op, `scripts/validate_support_weapon_authoring_snapshot.py`). The APW-1 impact set to a grenade's explosion, the
  AC-8 flak to an orbital shell's, the RL-77 cluster expiry removed and the W.A.S.P. recursion refusal are exercised on
  the snapshot (`scripts/validate_explosion_catalogue_snapshot.py`). Nothing is live-tested.
- **Not this.** These are shared row writes, like the primaries'. A payload for one weapon's shots alone, without
  touching the row (`hd2.projectiles.payload`), is 0.32.0 work.

## Payload options (0.31.2)

Every value a payload field takes, for an editor's picker, grouped by where the explosion comes from. Offline
metadata (`domains/payload_options.lua`, `sdk/PayloadOptions.json`, generated by
`scripts/generate_payload_options.py`); no raw ids.

```lua
-- One field: its own explosion, none and every option it takes, each with the value to write and its acknowledgements.
local o = hd2.support_weapon('AC-8 Autocannon'):attack('programmable'):projectile():terminal_action('impact')
    :payload_options()
for _, item in ipairs(o.options) do
    mod:log(item.group_label .. ': ' .. item.label .. ' ' .. table.concat(item.warnings, ','))
end
-- Every option a payload accepts, optionally filtered.
hd2.explosions.payload_options({group = 'hellbomb'})
```

- `hd2.explosions.payload_options(filter)`: every catalogued explosion a payload accepts, in display order, as `{name,
  label, owner, group, group_label, family, damage, durable_damage, inner_radius, outer_radius, statuses,
  lingering_field, fire, shrapnel, arc, warnings, shared_row, package {mission, loaded_by_runtime, via, objective,
  packages}, acknowledgements, value, note}`; `value` is `hd2.explosion(name)`. `note` says why an option's label differs
  from the catalogue's.
- `hd2.explosions.payload_options(terminal, filter)` and `terminal:payload_options(filter)` (primary, secondary and
  support terminal actions): `{field, resource, weapon, attack, phase, current, current_label, editable, reason,
  shared, acknowledgements {own, none, catalogue}, own, none, options, excluded, groups}`. `own` and `none` carry the
  value to write; the options leave out the field's own explosion and list `excluded` ones with the reason. On a
  primary, an option that is another primary's own explosion keeps that weapon's handle (`via = 'weapon_handle'`):
  it needs only the field's acknowledgements and loads that weapon's package, as before.
- Filters: `group`, `search` (name, label or owner), `warning`, `without_warning`.
  `hd2.explosions.payload_groups()` and `hd2.explosions.payload_warnings()` give the groups and warning texts.

| Group | Options |
| --- | ---: |
| Primary and secondary weapons (`weapon`) | 18 |
| Support weapons (`support_weapon`) | 31 |
| Grenades and throwables (`throwable`) | 23 |
| Orbital strikes (`orbital`) | 13 |
| Eagle strikes (`eagle`) | 12 |
| Hellbombs (`hellbomb`) | 2 |
| Sentries and emplacements (`sentry`) | 7 |
| Mines (`mine`) | 4 |
| Vehicles and exosuits (`vehicle`) | 11 |

139 options: every catalogued explosion whose package is known (`payload = true`). The other 102 named explosions
(most enemy explosions, whose effects ship in faction content) are refused as payloads (`ASSET_UNAVAILABLE`). 14
options are in the mission effects package (no load). An explosion is a
row of one ExplosionSettings table that the game looks up by type whatever requests it, so an option's source family
does not limit it: a Hellbomb's or an orbital shell's explosion works from a projectile's impact like a weapon's.

**Warnings** (`warnings`, texts from `payload_warnings()`): `very_large` (2000 damage or more, or an outer radius of
20 m or more: 18 options, the Hellbombs among them, 10000 damage), `lingering_field` (a status field the explosion
leaves; the game holds at most 4096 and does not check the count, so avoid it on fast-firing weapons: 12), `fire`,
`shrapnel`, `arc`, `no_damage`, `objective_packages` (two objective packages of about 300 MB load before the write:
1, the nuke below). They inform; none is a refusal.

### EXCESSIVELY LARGE NUKE (0.31.2, offline only)

The payload option labelled `EXCESSIVELY LARGE NUKE` (group `other`, name `entity/cyborg_production_unit/ability`) is
the blast of the MS-N223 Shredder Silo's nuclear missile (`proof/ShredderSiloExample`, `silo.blast = 'Cyborg Production
Unit'`): the Cyborg Production Unit's explosion, the native catalogued row, unmodified. The silo writes nothing to it;
it requests that same explosion where its missile detonates. 10000 standard and durable damage, AP 10, demolition 60,
a 50 m inner and a 100 m outer and shockwave radius, no shrapnel, no status field, no fire. The option has the same
values, rules and acknowledgements as every catalogued payload (`allow_unverified_reference`,
`allow_unverified_effect`, the field's own), and warnings `very_large` and `objective_packages`.

- **Its packages.** Its effect ships only in an Automaton objective package that holds the whole production unit
  (about 217 MB), and its sound in a second objective package (about 81 MB). Before 0.31.2 the catalogue knew only the
  first as its package and refused the explosion as a payload, because its sound would have been missing. Since 0.31.2
  the catalogue entry lists both (`package.keys`). A payload write, an attack output slot and a custom projectile row
  load both before the write (`core/assets.lua` `explosion_dependencies`). These are the same two packages the silo
  loads for the same explosion.
- **Why it is safe to offer.** Both packages are in this build's bundle database. Loading them through the game's
  package system during a mission and then requesting this explosion was seen live with the silo
  (`schemas/live_evidence.json` `custom_stratagem_silo`: drawn and sounded, on the host and on a client). A payload
  write only references the row: its live settings row is re-proven first (type, damage link, radii), and nothing is
  written to it. It releases no shrapnel, so no chain can make a projectile spawn itself.
- **Not live-tested as a payload.** The game setting it off from a projectile's impact (instead of a request) has not
  been seen live, so it stays behind `allow_unverified_reference` and `allow_unverified_effect`.
- **Cost.** About 300 MB load before the write, which can take up to 90 s and cause a hitch. They stay loaded for the
  session. With other players, each compatible Runtime loads them too (`runtime/asset_sync.lua`), as for every payload.
- **Range.** Anything within 100 m of the impact is caught, the shooter included: give it to a weapon that fires far
  (the APW-1, a rocket), never to one fired at close range. Every round sets one off.

**Packages.** Choosing an option loads its package before the write: the operation waits (`waiting_for_assets`) and
writes once the package is resident. A mission effects option needs no load. A package that is not resident after
90 s, or that cannot be requested (the 64-package budget, a failed proof, a runtime without package loading), rejects
the operation with `ASSET_UNAVAILABLE`: the row keeps its value and nothing is written (docs/asset-loading.md). In a
lobby, the package is shared with the compatible Runtimes (synced asset loading; development, not live-proven), so
their games can draw the effect; the payload itself changes only the rows of the machines running the mod.

**Refusals per field** (`excluded`, `fields[].excluded` in the SDK file): an explosion whose shrapnel chain releases
the row the field writes. One today: the W.A.S.P. cluster explosion on the W.A.S.P.'s own row. The write path
re-proves the chain live in any case.

## Requesting an explosion

```lua
hd2.explosions.spawn('stratagem/orbital_gas_strike/shell_impact',
    {position = event.position, allow_unverified_effect = true})
```

`hd2.explosions.spawn(explosion, opts)` and `hd2.explosions.prepare(explosion, opts)` accept every catalogued explosion
with `spawn = true` (its type proven against the settings table and its package known): 141 explosions. The reviewed
spawn set (the three named explosions and the 13 catalogued weapon explosions; `reviewed_spawn = true`) works without
an acknowledgement, by its reviewed name or its catalogue name, exactly as before; every other one needs
`opts.allow_unverified_effect = true` (`UNVERIFIED_EXPLOSION` otherwise). The rules of docs/event-scripting.md apply
unchanged: host only, in a mission, credited to the local player, 6 at once and 1 a second per mod, cause depth,
assets loaded first. An explosion whose effect ships in the mission effects package is requested only while that
package is resident (`ASSET_UNAVAILABLE` otherwise; it always is in a mission). The custom silos keep the reviewed set.

## Not live-tested

Pending entries in `schemas/live_evidence.json`: an edit through `hd2.explosion(name)`, a catalogued explosion as a
terminal explosion and as an attack output slot, and a spawn outside the reviewed set. The example project
`examples/projects/ExplosionCatalogueTest` exercises all three.
